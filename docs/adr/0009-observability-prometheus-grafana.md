# ADR-0009: Observability with Prometheus, alert rules as tested code, and Grafana

- **Status:** Accepted
- **Date:** 2026-10-01
- **Deciders:** Project team

## Context

The brief asks for a pipeline that is observable, not just functional:
structured logging across stages, and at least one alert or health-check
rule. The questions an operator of this system actually asks are more
specific than "is it up":

1. Is the real-time view fresh? Requirement R1 promises provisional figures
   no older than 60 s.
2. Is every zone reporting, or has a feeder gone quiet while the rest of the
   grid carries on?
3. Is solar contributing as expected while the sun is high? This is the use
   case's own alert.
4. Are we rejecting an unusual share of readings, which points to an
   upstream firmware or schema fault?
5. Is every ended day being settled, and if not, is a refused drop the
   reason?

Structured JSON logs, correlation ids, per-component Prometheus endpoints
and the `ops.*` run tables were built with each component (Sections 4–8).
This record decides how those signals become **alerts** and **one
operations view**.

## Decision

**Prometheus scrapes every component and evaluates the alert rules. The
serving API exports the business state only the serving store knows.
Grafana shows it all on one provisioned dashboard.**

- **Pull, not push.** Each component serves `/metrics`: the producer on
  :9101, the batch source on :9102, the speed layer on :9103, and the API on
  :8000. Prometheus scrapes all of them every 10 s. A component that dies
  shows up as `up == 0`, which a push model cannot distinguish from a quiet
  period.
- **Business state comes from the serving API.** No component knows how old
  ZONE-C's latest figure is, or how many ended days are still unsettled.
  Only the serving store does. The API computes these at scrape time
  (`serving/metrics.py`), through the same queries it serves:
  - per zone: freshness, solar share and load
  - the speed layer's lag
  - the settlement backlog and the days blocked by a refused drop

  The alert rules and the dashboard therefore judge the same figures. The
  solar-share floor is exported from `Settings`, so the rule and the
  business dashboard share one threshold.
- **Alert rules are code, and tested.** Eight rules live in
  `infra/prometheus/rules/smartgrid.yml`, each naming the failure it catches
  and what to do. `promtool` unit tests (`infra/prometheus/tests`) feed
  synthetic series and assert exactly when each rule fires. They also assert
  when it must *not* fire: no solar alert at night, and no six-zone alert
  storm when the whole speed layer is stale. A test was mutated to confirm
  the suite fails when a rule is wrong.
- **Thresholds are tied to requirements or measurements, not taste:**

  | Rule | Threshold |
  |---|---|
  | Freshness | 60 s, from R1 |
  | Rejection rate | 5 %, against a measured 0.7 % baseline |
  | Settlement overdue | 360 s, more than a simulated day later than the measured 90 s |
  | Solar floor | 30 % between 10:00 and 14:00, calibrated on the simulation's midday zone shares of 25–180 % |

- **Real seconds for thresholds.** Operators live on the wall clock. Ages
  and lags are exported in real seconds, converted from simulated time with
  the shared clock's compression, and named so (`*_real_seconds`).
- **Grafana is provisioned, and the dashboard is generated.** The data
  source and dashboard are provisioned at startup. The dashboard JSON is
  generated by `scripts/build_grafana_dashboard.py`, so a panel change is a
  reviewable diff of a few lines. Colours follow identity in the validated
  palette order, and each panel has one axis.

## Alternatives considered

### Alertmanager for routing and notification

It gives deduplication, grouping, silencing and routing to e-mail or chat,
and a production deployment would add it. It was rejected here because
there is nobody to notify in a local demo. Firing alerts are visible in
Prometheus and on the Grafana dashboard. Adding Alertmanager later changes
routing only, not the rules.

### Grafana-managed alerting instead of Prometheus rules

It keeps alerts beside the panels and has a friendly UI, but it was
rejected. The rules would live in Grafana's database, or in provisioning
YAML that no tool can unit-test. Prometheus rules are plain files, run
without Grafana, and are tested by `promtool`.

### A separate exporter process for business state

It would give a cleaner separation, but it would also be another container,
another database connection pool, and a second copy of the serving queries
that could drift from the API's. The API already reads exactly this state
and is already scraped, so the collector reuses its queries.

### Log-based alerting (Loki or ELK)

The structured JSON logs make this possible. It was rejected on footprint:
the stack already needs about 6 GB. A log store would add another stateful
service, for alerts that metrics express more cheaply. The logs remain
machine-readable, with correlation and request ids, for diagnosis once an
alert fires.

## Consequences

**Positive**

- Every requirement with a number in it has an alert with that number.
- Alert logic is verified before it is deployed, including its silences.
- The business dashboard, the API and the alerts agree on every threshold.
- A new operator sees the whole pipeline on one page.

**Negative**

- The API now serves operations as well as consumers. A slow serving-store
  query slows the scrape, and an API outage takes the business-state
  metrics with it. `ServingStoreDown` and `ScrapeTargetDown` cover this.
- The two sources run on the host, so Prometheus reaches them through
  `host.docker.internal`, which a host firewall can block.
- Grafana's panel colours are fixed hex. They are chosen for the light
  theme (the default), and are not re-stepped for dark mode as the
  Streamlit dashboard's are.

## Revisit if

- The system gains operators to notify: add Alertmanager.
- Serving-store queries get slow enough to affect scrapes: move the
  collector into its own exporter with cached results.
- Log volume or retention requirements grow: add a log store and move
  diagnostic queries there.
